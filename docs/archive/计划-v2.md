# One · 三家合一规划 v2

> 2026-11-01 基于《计划.docx》整理。意图：以对话框为入口的个人成长系统——
> 下面聊天、上面气泡仪表盘（日期 / 今日任务 / 本周任务 / 弹性任务进度条），
> 一句话录入成果或排期，AI 返回可交互卡片（撤销 / 确认 / 进详情），详情页点击可改，
> 统计 + AI 分析，日志保留原话 + AI 浅色补充版。最终形态 app，先做网页端。

## 0. 三家合一的映射

| 来源 | 带进 One 的东西 | 形态 |
|---|---|---|
| 拾光（study-web） | **宿主**：Vue3 + SpringBoot + MySQL + Redis、JWT、AI 多轮对话建规划、日报、打卡、趋势/热力图、评分 | 直接在其代码库上扩展 |
| StudyLog（CF） | 日志/时间线的产品精神 + **公开分享页** | One 稳定后做一个只读公开层 |
| QQ bot（kaoyan 插件） | **工程纪律**：日期由代码解析（47 用例移植）、服务端校验、撤销栈、教练式追问提示词 | 移植为后端逻辑与 prompt |
| OneKichan | 详情页 / 主屏的**设计参考**（只借设计不借代码，那是独立纪律项目） | 视觉与交互参照 |

## 1. 两个原始问题的答案

**Q1 任务太多占不满怎么办？**
主屏气泡区是仪表盘摘要而非完整清单：
- 今日必现：日期 + 今日任务 ≤3 条（超出折叠成「本周还有 x 项」胶囊）+ 弹性任务 top2 带进度条
- 聊过的卡片钉在对话流里，不占气泡区；气泡区任意项点击 = 进详情页
- 原则：只显示「现在该看的」，满了不是问题，稀释才是

**Q2 自然语言功能上限没法教学？**
不教语法，教确认，三层机制：
1. AI 猜 + 卡片确认：一切写操作先出卡片，改字段再落库，猜错零成本
2. 输入框上方常驻快捷 chips：记一笔 / 排期 / 写日报 / 看统计（既是快捷键也是活教程）
3. 空态引导：每个空区域一句示例话术（「试试说：我刚学了数学两小时」），在哪空教哪
- 配套：撤销按钮永远在 → 用户敢随便说

## 2. 必须先定的决策（P0）

1. **宿主 = 拾光代码库**（不新起炉灶，重合 ~70%）
2. **弹性任务数据模型**（拾光现有任务模型是截止型的，缺累计型）：
   ```
   FlexibleTask { 名称, 别名[], 目标(总时长|次数), 周期(累计|每周|每日), 打点[] }
   TimeEntry { id, taskId, 分钟数, 日期, 来源消息id, 备注, createdAt }
   ```
   - 录入：LLM 抽意图 → 按别名匹配任务 → 匹配不到则反问「计入哪个/新建？」
   - 撤销 = 删打点（带来源消息 id，可精确撤）
   - 「明天开始都+2h」= 排期层操作（改计划），不是打点，走两步确认
3. **对话协议**：LLM 只做意图抽取输出结构化 actions JSON；
   **日期解析、校验、落库全在服务端**（LLM 只输出 day 标记：today/yesterday/weekday:N/YYYY-MM-DD）
4. **社交层冻结**：好友/私信/成就先不展示，One 第一性是单人工具
5. **客户端路线**：响应式网页 → PWA（可装主屏）→ Android 壳（WebView + 推送）

## 3. 分期路线

### P1 核心闭环（做完产品就活了）
- 主屏布局：对话框 + 气泡仪表盘（含折叠规则）
- 一句话录时长 / 建任务 / 撤销，卡片确认交互
- 弹性任务进度条实时联动
- 验收：发一句「我刚刚学了数学两个小时」→ 卡片 → 撤销 → 重发 → 进详情看到打点

### P2 排期与详情
- 排期对话：「我有个新任务下周交成果，帮我排期」→ 草稿卡片（任务+时间块）→ 确认
- 详情页：照 OneKichan 风格 + 点击即改（任务字段、打点、日程）
- 硬规则：AI 改计划必须过卡片确认（守住拾光「无自动重排」边界）

### P3 统计与日志
- 统计页：拾光趋势/热力图复用 + AI 分析卡（每周一评，含弹性任务达成率）
- 日志：一句话 + AI 补全（用户可选答 AI 追问）；版式 = 原话 → 横线 → 浅色 AI 完整版
- 验收：连续记 7 天后 AI 分析卡能引用真实数据

### P4 出海
- PWA：manifest + Service Worker + 主屏图标
- 提醒推送（Web Push）+ 每日早报 / 周报定时任务（拾光 Redis 限流已有）
- Android 壳（WebView + 推送桥），参照 OnekichanApp 的壳思路

## 4. 数据迁移

- 权威库 = 拾光 MySQL
- bot 的 D1 数据（kaoyan 计划 + study 台账）：写一次性导入脚本 → 弹性任务/打点
- StudyLog CF：保留为公开分享页（从 One 导出只读快照），不迁移

## 5. 风险与对策

| 风险 | 对策 |
|---|---|
| 语义理解边界 case 多 | 一切写操作过卡片；别名匹配失败就反问；LLM 永不直接产日期 |
| LLM 成本（深度思考贵） | 意图抽取用便宜模型，日报评估/周报才用思考模式（拾光已有此分层） |
| scope 膨胀（拾光功能全保留） | 社交层冻结；每期只验收列出的一条 |
| 两套账号体系（StudyLog 令牌 vs 拾光 JWT） | StudyLog 降级为只读公开层后自然消解 |
| app 期望管理 | P4 前用 PWA 顶住「能装主屏」的需求 |
